2D老师与对话系统开发总结

教学表现系统 | 2025/12-2026/02 | 对话图驱动与角色动作联动设计

系统概述

这个项目把 2D 老师系统 和 对话系统 视为一个统一的“教学表现系统”来理解。对话系统负责推进叙事、节点状态和分支逻辑，2D 老师系统负责角色动作、讲解节奏和情绪表现，两者通过节点参数、动作参数或事件桥接来联动。

当前代码中，这两套能力都已经具备较完整的基础实现，但还没有完全硬接在一起。也正因为如此，这个项目的重点不只是“做了什么”，更在于说明现有架构如何自然演进成一个适用于教学、讲解和问答引导的互动对话表现框架。

当前系统边界

  • 两套系统当前是并列存在的独立模块，架构兼容，但代码层尚未直接互相 import 调用。

  • 对话数据结构已经预留了 `animation`、`emotion`、`actions` 等字段，说明后续联动并不需要推翻现有设计。

  • 事件系统已经提供了 `NodeStarted`、`DialogueStarted`、`DialogueEnded` 等天然桥接点，适合做低耦合联动。

  • 从工程阶段看，这属于“架构上已兼容，业务上待接线”的状态，非常适合在文档与答辩中强调设计前瞻性。

对话系统的关键点

数据驱动节点图

对话系统的核心不是简单显示文本，而是由 `DialogueData`、`DialogueNode`、`DialogueChoice` 组成的有向节点图。节点通过 `nextNodeId` 和选项跳转形成完整流程。

“注册 node” 的真实含义

当前并没有注册节点类型的机制，真正被注册的是整段对话资源。`json.nodes` 会被转换成 `Map<string, DialogueNode>`，由 `DialogueManager` 在运行时查找和推进。

运行时状态机

`DialogueManager` 统一管理 `_dialogues`、`_currentNode`、`_state`、`_history` 等状态，使对话具备资源仓库、状态机和节点调度器三重职责。

动作接口已预留

`ActionType.PLAY_ANIMATION` 已经存在，这意味着“对话控制老师动作”并不是新增系统，而是把已有预留接口真正接到 `teacher2DService` 上。

2D老师系统的关键点

数据层 `teacher2DData`

通过 `Animation2DType`、`Animation2DMode` 和默认配置表，构建了一套动作词典。对话层只需要传递语义化动作，不需要关心底层动画名。

服务层 `teacher2DService`

统一对外提供播放接口，保存当前动画状态，并把请求转发给真正的动画控制器，是老师系统的唯一调用入口。

表现层 `teacher2DItem`

挂在场景节点上，负责把 `cc.Animation` 或 `sp.Skeleton` 适配为统一接口，让服务层不被底层引擎组件耦死。

联动意义

对话系统并不需要知道老师是帧动画还是 Spine，只需要告诉服务层“播放哪种动作”，这使后续联动保持轻量且可扩展。

推荐联动方案

结合现有实现，我更推荐把这个项目描述为“节点字段 + 动作系统并存”的最终工程方案。`node.animation` 用来描述节点的默认表现动作，`actions.playAnimation` 用来表达额外触发的一次性动作，这样既保留了配置直观性，也兼顾了扩展能力。

  • 推荐接线点一：`NodeStarted`。增加 `DialogueTeacher2DBridge` 监听节点进入，读取 `node.animation` 并映射到 `Animation2DType`，这是最轻量、最符合现有架构的方案。

  • 推荐接线点二：`executePlayAnimation`。在动作系统里真正实现 `PLAY_ANIMATION`，适合处理选项点击、奖励反馈和特殊强调动作。

  • 推荐映射方式：使用字符串映射表，例如 `"talk"` 对应 `Animation2DType.TALK`，既方便策划配置，也便于后期统一维护。

实际界面效果

下面两张图展示了当前系统在实际项目里的界面表现：一张体现带选项分支的对话场景，另一张体现继续推进时的基础讲解界面。它们能够直接说明“对话内容 + 老师表现”这个统一系统的使用场景。

带选项分支的商店对话界面：右侧老师角色负责表现，底部对话框负责文本展示，右上角选项区负责分支跳转。

基础推进界面：当节点没有选项时，系统通过继续按钮或自动播放推动下一个节点，老师角色则保持讲解态或待机态。

统一系统总体架构图

flowchart TB subgraph 数据层 DD[DialogueData / DialogueNode / DialogueChoice] TD[teacher2DData / Animation2DConfig] end subgraph 逻辑层 DM[DialogueManager] DC[DialogueConditionManager] DA[DialogueActionManager] TS[teacher2DService] end subgraph 表现层 DUI[DialogueUI] TItem[teacher2DItem] end subgraph 桥接层 EV[EventManager] NS[Events.NodeStarted] PA[ActionType.PLAY_ANIMATION] end DD --> DM DM --> DC DM --> DA DM --> EV EV --> DUI TD --> TS TS --> TItem NS --> TS PA --> TS

这张图强调的是统一系统的层次划分。对话数据和老师动画配置分别作为数据源进入逻辑层，再由 UI、角色组件和事件系统协同完成“讲什么”和“怎么讲”的组合表现。

对话加载与节点注册流程

flowchart TD A[外部 JSON 对话数据] --> B[DialogueManager.loadDialogue] B --> C[DialogueDataImpl.fromJSON] C --> D[把 json.nodes 转成 Map<string, DialogueNode>] D --> E[DialogueDataImpl.validate] E --> F{校验通过?} F -->|否| G[输出错误并返回 null] F -->|是| H[存入 _dialogues: Map<string, DialogueData>] H --> I[RaiseEvent DialogueLoaded]

这里解释了你文档里提到的“注册 node”到底是什么。系统并不是注册节点类型，而是把整段对话资源加载进 `DialogueManager`，并把节点表构造成可检索的 `Map`，供运行时按 `id` 推进。

2D老师播放链路

flowchart TD A[外部调用 teacher2DService.playAnimation] --> B[根据 Animation2DType 查配置] B --> C{配置存在?} C -->|否| Z1[返回 false] C -->|是| D{animationController 已注入?} D -->|否| Z2[返回 false] D -->|是| E[更新 animationState] E --> F[调用 controller.playAnimation] F --> G{当前模式} G -->|cc.Animation| H[buildCocosAnimController] G -->|sp.Skeleton| I[buildSpineController] H --> J[真正播放动画] I --> J

这张图说明老师系统为什么适合被对话系统接入。服务层只负责接收动作语义并转发给控制器，底层到底是 `cc.Animation` 还是 `sp.Skeleton`，对外部调用方来说都是透明的。

节点参数驱动老师动作

flowchart TD A[DialogueManager.playNode node] --> B[RaiseEvent NodeStarted node] B --> C[DialogueUI.showNode node] B --> D[DialogueTeacher2DBridge.onNodeStarted] D --> E{node.animation 存在?} E -->|否| F[不处理] E -->|是| G[字符串映射到 Animation2DType] G --> H[LogicSys.getService teacher2DService] H --> I[teacher2DService.playAnimation] I --> J[teacher2DItem 真正播放角色动作]

这是当前最推荐的联动方式：在节点进入时读取 `node.animation`，再通过一个薄桥接层把字段映射到老师动作。这样既不污染 `DialogueManager` 核心逻辑，也不会让 UI 去承担系统联动职责。

关键模块

  • DialogueManager：管理对话资源、状态机与节点推进流程。
  • DialogueData / DialogueNode：构成数据驱动的有向节点图模型。
  • teacher2DService：统一对外暴露老师动画播放接口。
  • teacher2DItem：适配 `cc.Animation` 与 `sp.Skeleton` 两类底层动画实现。

当前状态与价值

价值：对话系统已经具备完整的数据结构、校验机制、分支逻辑和状态管理，不是简单的文字面板。

价值：2D 老师系统通过配置表 + 服务层 + 控制器接口完成了解耦，后续接入不会牵动底层表现代码。

现状：两套系统尚未直接接线，但从字段、事件和动作接口上看，联动条件已经齐备。

建议：优先通过 `NodeStarted` 增加桥接模块，再逐步在 `PLAY_ANIMATION` 动作里补完整执行逻辑。
