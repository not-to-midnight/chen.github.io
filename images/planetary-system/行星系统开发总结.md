# 行星系统开发思路与实现细节总结

本文档基于当前项目中的行星系统实际实现整理，目标是把系统的设计目标、模块职责、运行流程、物理计算、UI 交互、相机控制、资源结构、已知边界与后续扩展方向完整总结出来，方便后续继续开发、答辩汇报、系统重构和新成员接手。

## 1. 系统目标

行星系统不是一个单纯的“轨道动画演示”，而是一个集成在 Cocos Creator 项目里的可编辑、可模拟、可观察、可交互的三维物理教学模块。它要解决的核心问题有四类：

1. 在编辑阶段允许用户自由搭建天体系统。
2. 在运行阶段基于简化万有引力模型推进天体运动。
3. 用图形化方式展示轨道、受力、质心等物理现象。
4. 让用户能够通过相机和 UI 对系统进行观察、聚焦和调整。

从项目用途看，这个系统更偏“教学可视化”和“可交互实验”，而不是追求天文学意义上的高精度模拟。因此在设计上优先考虑：

- 可理解性
- 可调试性
- 可演示性
- 实时性能
- 与当前 UI/事件系统的低耦合集成

---

## 2. 总体架构

整个行星系统采用的是“服务层统一管理 + 组件自注册 + 事件驱动 UI + 控制器驱动相机”的结构。

### 2.1 核心分层

可以把系统拆成五层：

1. 启动与服务注册层  
   负责在游戏启动时注册 `PlanetService`，保证系统具备唯一的物理核心实例。

2. 物理仿真核心层  
   由 `PlanetService` 统一管理所有天体对象、引力计算、积分推进、质心、重置逻辑。

3. 天体实体层  
   由 `PlanetItem`、`StarItem`、`BallItem` 构成，负责承载单个天体的状态与表现。

4. UI 交互层  
   由 `PlanetUI` 与 `PlanetPropertyItem` 组成，负责按钮、参数面板、增删实体、状态切换。

5. 观察与输入层  
   由 `FreeCameraController` 与 `SkyController` 负责每帧驱动、相机操作、射线拾取与聚焦。

### 2.2 核心设计思想

当前系统最重要的设计思想有四个：

#### 1. `PlanetService` 是唯一真相源

所有“系统级状态”都收敛在 `PlanetService` 中，例如：

- 当前有哪些行星
- 当前有哪些恒星
- 是否存在恒星
- 当前是否处于三星模式
- 当前模拟状态是编辑、运行还是暂停
- 物理更新怎么推进
- 初始位置怎么记录
- 质心怎么计算

这样做的好处是：

- UI 不直接计算物理
- `PlanetItem` 不直接管全局系统
- 相机控制器只读系统状态，不碰计算细节
- 后续改算法时，改动面更集中

#### 2. 行星/恒星组件采用“自注册”

`PlanetItem.onLoad()` 会注册到 `PlanetService`。  
`StarItem.onLoad()` 也会注册到 `PlanetService`。

这样不需要场景管理器在外部手工维护实体列表，谁被实例化进场景，谁就主动进入系统。

#### 3. UI 与逻辑通过事件解耦

系统没有让 `PlanetUI` 直接硬绑定所有行星实体，而是通过事件广播来同步：

- `PlanetUpdated`
- `FocusPlanetChanged`
- `PlanetBodyPositionChanged`
- `resetGame`

这样修改位置、删除对象、切换聚焦、重置游戏时，表现层和逻辑层之间不会形成强耦合。

#### 4. 模拟采用固定步长，不直接用帧时间积分

系统不是直接拿 `dt` 做一次“随帧积分”，而是：

- 维护一个累加器 `_accumulator`
- 固定物理步长 `FIXED_DT = 1 / 120`
- 在 `update(dt)` 里循环执行多个固定步

这样可以明显提升轨道模拟的稳定性，避免帧率波动直接污染物理结果。

## 3. 启动与接入流程

### 3.1 游戏入口

项目启动入口是 `assets/Scripts/startboot.ts`。

其中：

- `LogicSystem.init()` 会初始化全局服务系统。
- `PlanetService` 会在 `LogicSystem` 中被注册。
- 当 `level=3` 时，会进入星球场景。

### 3.2 服务注册

`assets/Scripts/LogicSystem/LogicSystem.ts` 中，`PlanetService` 被列入统一注册列表：

- `QuizService`
- `teacher3DService`
- `teacher2DService`
- `PlanetService`

这说明行星系统并不是一个孤立脚本，而是项目主逻辑系统中的正式模块。

### 3.3 星球关卡进入条件

`startboot.ts` 中：

- `level.star = 3`
- `getSceneName(3)` 返回 `star`
- `initStar()` 会确认 `PlanetService` 已经存在
- 场景预加载成功后进入 `assets/scene/star.scene`

这套接入方式说明行星系统天然支持：

- 单独场景运行
- URL 关卡切换
- 与其他子系统并行共存

## 4. 主要模块职责拆解

## 4.1 `BallItem`

路径：`assets/Scripts/CoreManager/physical/planet/ballItem.ts`

这是行星与恒星的公共基类，只保留最基础的两个物理身份字段：

- `id`
- `mass`

它本身不负责任何逻辑，目的是提供统一父类，便于 `PlanetService` 的引力计算以统一接口使用天体对象。

### 为什么需要基类

因为引力计算本质上对“行星”和“恒星”是一致的，都需要：

- 位置
- 质量
- ID

用基类后，`calculateGravity(body1, body2)` 就能统一复用。

---

## 4.2 `StarItem`

路径：`assets/Scripts/CoreManager/physical/planet/starItem.ts`

恒星组件职责很纯粹：

- 提供质量属性
- 在 `onLoad` 时注册到 `PlanetService`
- 在销毁时从 `PlanetService` 注销

### 设计特点

1. 恒星不承担速度、力、轨迹等字段  
   当前实现里恒星更像“引力源”，而非完整参与积分推进的运动体。

2. 恒星数量被限制为最多一颗  
   在 `PlanetUI.onAddStarButtonClicked()` 中，如果已有恒星则直接提示不可再加。

3. 一旦有恒星，系统的引力模型会切换到“恒星影响行星”的简化模式  
   这在 `PlanetService.calculateForce()` 中体现得很明确。

### 这意味着什么

当前项目里的“太阳系模式”本质上是：

- 一颗恒星固定在系统中
- 多颗行星围绕恒星运行
- 不考虑行星之间的相互引力

这是一个典型的教学简化模型，非常适合展示基础轨道。

---

## 4.3 `PlanetItem`

路径：`assets/Scripts/CoreManager/physical/planet/planetItem.ts`

这是单颗行星的核心组件，职责最多，可以分成四部分。

### 4.3.1 基础物理状态

每颗行星保存：

- `mass`
- `initialVelocity`
- `velocity`
- `force`
- `acceleration`
- `isStopped`

其中：

- `initialVelocity` 是用户在面板里填写的“初始附加速度”
- `velocity` 是模拟运行时真正参与积分的即时速度
- `force` 和 `acceleration` 由 `PlanetService.updateAllForce()` 统一刷新

### 4.3.2 注册与注销

在 `onLoad()` 中：

- 先向 `PlanetService` 注册自己
- 再绑定碰撞器事件

在 `onDestroy()` 中：

- 从 `PlanetService` 注销

这种模式使得场景中的行星实例和服务层的注册表始终同步。

### 4.3.3 编辑器联动

在编辑器环境下：

- `onEnable()` 监听 `Node.EventType.TRANSFORM_CHANGED`
- 节点一旦被拖动，就调用 `PlanetService.onEditorPlanetPositionChanged(this)`

这套逻辑是“三星等角布局”的关键入口，说明该系统不仅支持运行时模拟，也支持编辑态的空间布局辅助。

### 4.3.4 轨迹与受力可视化

`PlanetItem.updateState()` 会：

- 取主相机上的 `geometryRenderer`
- 如果 `renderForce = true`，调用 `drawForceArrow`
- 如果 `renderOrbit = true`，调用 `recordTrail` 与 `drawTrail`

其中：

- 力箭头是红色
- 轨迹线是绿色
- 轨迹点会保存在 `_trail` 数组中，长度上限 600

### 4.3.5 碰撞策略

发生碰撞时：

- `isStopped = true`
- `velocity = 0`
- `acceleration = 0`

这说明系统当前采用的是“碰撞即停”的处理方式，而不是：

- 弹性碰撞
- 合并质量
- 碎裂
- 吞噬

这是一种很稳妥的教学演示方案，但也意味着系统目前没有复杂天体碰撞模型。

### 4.3.6 当前代码里的一个细节问题

`planetItem.ts` 中存在一行：

`@property({ type: Vec3, tooltip: '初始速度' })i`

这个 `i` 很像误输入字符。  
如果当前构建没有报错，可能是本地编译器处理容错或尚未触发问题，但从代码规范上看，这里应该尽快清理。

## 4.4 `PlanetService`

路径：`assets/Scripts/CoreManager/physical/planet/PlanetService.ts`

这是整个行星系统最关键的类。它承担了：

- 实体注册
- 力学计算
- 固定步长积分
- 起始圆轨道速度估算
- 三星布局同步
- 初始位置记录与重置
- 质心计算与显示
- 聚焦目标管理

它本质上是行星系统的“仿真核心 + 系统协调中心”。

下面拆开详细说。

---

## 5. `PlanetService` 的数据管理机制

### 5.1 注册表

系统内部维护两个注册表：

- `_planetItems: Map<number, PlanetItem>`
- `_starItems: Map<number, StarItem>`

同时有：

- `_nextPlanetId`
- `_nextStarId`

用于生成唯一 ID。

### 5.2 注册清理

`pruneInvalidRegistry()` 会检查：

- 实体组件是否还有效
- 节点是否仍然存在

无效对象会被自动移出注册表。

这个设计很重要，因为在 Cocos 里：

- 节点可能已 destroy
- 组件可能已失效
- 但引用还可能暂时存在

如果不清理，服务层很容易出现野引用，导致计算出错。

### 5.3 系统状态

`PlanetService` 维护了多个系统状态字段：

- `_simulationStarted`
- `isThreePlanets`
- `_hasStar`
- `_stimulateState`
- `_currentPlanetId`

其中 `StimulateState` 枚举包括：

- `Normal`
- `Stimulate`
- `Pause`

这构成了系统最核心的状态机。

## 6. 物理模型设计

## 6.1 引力常数

系统中定义：

```ts
export const G = 100;
```

这个值显然不是现实物理中的 SI 制引力常数，而是一个“工程缩放常数”。

### 为什么这样做

因为游戏中的单位通常不是：

- 米
- 千克
- 秒

而是一个视觉和交互友好的比例尺。

将 `G` 设成较大的值，可以让在有限场景尺寸下：

- 轨道运动更明显
- 速度和位移处于可观察范围
- UI 可调参数更直观

### 结论

当前系统追求的是：

- 相对合理的轨道关系
- 稳定可视的运动效果

而不是天文学精度。

---

## 6.2 引力计算公式

`calculateGravity(body1, body2, out)` 计算的是：

- `body1` 受到 `body2` 的引力
- 方向为 `body1 -> body2`

核心公式：

\[
F = \frac{G m_1 m_2}{r^2}
\]

实现步骤是：

1. 计算两者位置差向量
2. 求距离平方 `distSq`
3. 距离过小则直接返回零向量，避免除零
4. 单位化方向向量
5. 根据引力公式求标量大小
6. 方向向量乘以标量，得到力向量

这部分实现简洁而标准。

---

## 6.3 两种引力模式

`calculateForce(planet)` 里有一个非常关键的分支：

### 情况一：系统中有恒星

只考虑：

- 恒星对行星的作用力

不考虑：

- 行星对行星的作用力

这是一个明显的简化。

### 情况二：系统中没有恒星

计算：

- 行星之间的两两引力

这时系统会进入更接近 N 体问题的模式，但因为通常行星数量不会太大，所以复杂度仍可接受。

### 设计意义

这套设计体现了非常明确的产品取舍：

- 有恒星时，强调“围绕中心体公转”的演示效果
- 无恒星时，支持“双星/三星平衡系统”的实验观察

这也解释了为什么当前系统会特别对“双星”和“三星模式”做专门处理。

## 7. 数值积分方案

## 7.1 为什么不用简单欧拉

如果直接采用显式欧拉：

- 容易积累能量误差
- 轨道会发散
- 长时间模拟不稳定

对行星系统这种“持续转很多圈”的场景来说，这类误差会非常明显。

## 7.2 当前选型：Velocity Verlet

系统使用的是 Velocity Verlet 积分。

其单步流程是：

1. 旧加速度更新半步速度
2. 用半步速度更新全步位置
3. 在新位置上重新计算力和加速度
4. 再用新加速度补完后半步速度

### 这种算法的优点

1. 相比欧拉更稳定  
2. 能量误差更小  
3. 很适合轨道类系统  
4. 实现复杂度不高  
5. 配合固定时间步，运行效果很平稳

### 固定时间步

系统将：

```ts
private static readonly FIXED_DT = 1 / 120;
```

也就是物理计算按 120Hz 进行。

再通过 `_accumulator` 把帧时间切成多个固定步来跑。

### 这套设计的实际价值

即使渲染帧率波动，只要总体性能足够，物理结果仍较稳定，减少了：

- 帧率越低轨道越乱
- 不同设备上轨道不一致

这类问题。

## 8. 初始速度生成策略

在用户点击“开始模拟”时，`PlanetService.start()` 不只是切换状态，还会为系统自动计算一组“更合理的起始轨道速度”。

这部分是系统体验的关键，因为如果没有初始速度，天体往往会直接掉向中心或乱飞。

## 8.1 有恒星时

系统调用：

`calculateCircularMotionWhenHasstar(planet, star)`

速度公式对应的是经典圆轨道速度：

\[
v = \sqrt{\frac{GM}{r}}
\]

方向通过：

`Vec3.cross(Vec3.UP, R)`

获得切线方向，说明系统默认使用：

- `Y` 轴作为公转轴
- 天体主要在 `XZ` 平面中运动

### 额外设计

自动圆轨道速度会和 `planet.initialVelocity` 相加。

这意味着：

- 系统给一个基础稳定轨道速度
- 用户还能在此基础上手工叠加扰动速度

这非常适合教学演示，例如：

- 观察轨道偏心变化
- 观察速度改变导致逃逸或坠落

---

## 8.2 无恒星、两颗行星时

系统走双星公式：

`calculateCircularMotionWhenHasTwoPlanets(planet, otherPlanet)`

其目的是让两颗行星绕共同质心做圆周运动。

这里速度大小和“对方质量”有关，体现了：

- 质量越大的天体转得越慢
- 质量越小的天体转得越快

这符合双体系统的质心运动直觉。

---

## 8.3 无恒星、三星模式时

系统调用：

`calculateCircularMotionWhenHasThreePlanets(planet)`

这是一个为“三星等角布局”量身定制的简化平衡公式。

其前提条件是：

- 没有恒星
- 恰好三颗行星
- 已开启 `isThreePlanets`

速度相对系统质心计算，适合构造“三体平衡展示”。

### 需要注意

这个实现更偏展示用简化模型，而非严格意义上的通用三体求解。

它的价值在于：

- 演示等角分布下的视觉稳定状态
- 给用户一个可直接观察的三星系统初始解

---

## 8.4 其它构型

如果系统没有恒星，且行星数量不是 2，也没有开启三星模式，则：

- `start()` 不会自动生成轨道速度
- 系统主要依赖用户填写 `initialVelocity`

这是当前实现的边界之一。

### 这意味着

对“四星无恒星系统”或更多任意构型：

- 系统可以跑
- 但不会自动给出稳定初值

后续如果要扩展复杂系统，最优先需要补的就是这部分“初值生成策略”。

---

## 9. 三星模式与编辑器布局辅助

这是当前系统很有特色的一部分。

## 9.1 开启条件

只有满足：

- 没有恒星
- 恰好 3 颗行星

才能开启三星模式。

这个规则在 `PlanetUI.canEnableThreePlanetsMode()` 中明确限制。

如果条件不满足：

- toggle 会被自动重置
- 用户会收到提示

## 9.2 编辑器联动布局

`syncEqualAnglePlanetLayout()` 会把无恒星三星系统自动重排为：

- 以锚点行星为基准
- 所有行星处于相同半径
- 在同一 `Y` 值平面
- 沿圆周等角分布

### 关键思路

1. 找到锚点行星  
   可以是显式传入的，也可以根据“最近被移动的行星”判断。

2. 用锚点的位置确定：

- 半径
- 基准角度
- 轨道高度 `Y`

3. 其余行星按 `2π / count` 的步长自动排开

### 好处

- 用户只要拖一颗行星，系统就能自动形成三星等角布局
- 不需要手工算 120 度
- 视觉更规整
- 更容易进入稳定展示状态

### 适用范围

它主要服务于：

- 编辑器调试
- 教学展示
- 三星场景初始化

而不是通用布局算法。

## 10. 质心系统

## 10.1 质心计算

`calculateBarycenter()` 会遍历：

- 所有恒星
- 所有行星

按质量加权平均出质心：

\[
\vec{r}_{center} = \frac{\sum m_i \vec{r_i}}{\sum m_i}
\]

### 为什么重要

质心在这个系统里有两个用途：

1. 用于三星模式下的轨道速度计算
2. 用于相机 Follow 模式定位

## 10.2 质心可视化

当：

- 行星数量 >= 2
- 没有恒星

系统会生成一个小白球节点 `barycenter` 显示质心位置。

### 说明

这里的注释写着“更新质心小黑球的位置”，但材质颜色实际设成了白色，这反映出现阶段视觉文案和实现可能略有不一致。

### 重置行为

`resetGameToInitialPosition()` 时会销毁这个质心节点，避免重置后遗留旧可视化对象。

## 11. UI 系统设计

## 11.1 `PlanetUI`

`PlanetUI` 是整个模拟的主操作面板。

它管理：

- 开始模拟
- 暂停/继续
- 重置
- 三星开关
- 添加行星
- 添加恒星
- 属性面板列表
- 当前聚焦显示
- 当前状态显示

### 11.1.1 面板同步策略

`syncPanels()` 的实现很值得注意。

它不是简单“全部销毁后重建”，而是：

1. 遍历当前系统实体
2. 对已有面板执行刷新
3. 对缺失面板执行创建
4. 对多余面板执行删除

这是一种轻量级的“增量同步”思想。

好处：

- UI 不会每次全量闪烁
- 对已有节点更友好
- 逻辑更清晰

### 11.1.2 按钮状态控制

`updateButton()` 会根据 `StimulateState` 统一设置按钮可用性。

例如：

- 编辑中：可以开始，不能暂停，不能重置
- 模拟中：不能再次开始，可以暂停，可以重置
- 暂停中：不能再次开始，可以继续/暂停，可以重置

同时：

- 模拟中不允许添加行星
- 模拟中不允许添加恒星

### 11.1.3 三星开关保护

如果当前三星模式无效：

- 自动关闭
- 提示用户原因

而且在添加/删除行星、添加恒星等操作后，也会自动重置三星模式，避免系统处于非法状态。

---

## 11.2 `PlanetPropertyItem`

这是单个星体对应的一条属性行。

支持的字段包括：

- 质量
- 初始速度
- 位置
- 删除
- 是否显示轨道
- 是否显示力
- 力箭头缩放
- 箭头头部比例

### 行星与恒星共用一套面板

其 `initItem()` 能识别：

- `PlanetItem`
- `StarItem`

并通过 `applyStarMode(true/false)` 控制 UI 的显示隐藏。

例如恒星模式下会隐藏：

- 初速度输入
- 轨道渲染
- 力渲染
- 箭头参数

这是一种比较节省 UI 成本的复用方案。

### 位置更新方式

位置输入不是直接改节点，而是发事件：

- `RaiseEvent(Events.PlanetBodyPositionChanged, ...)`

然后交给 `PlanetService.updateBodyPosition()` 统一处理。

这是一个非常合理的做法，因为：

- 位置更新可能会影响三星布局
- 可能还需要触发 UI 刷新
- 可能影响系统状态同步

如果 UI 自己直接改节点，就会绕开这些系统性逻辑。

### 删除逻辑

删除前会检查：

- 当前是否处于编辑状态

如果不是编辑状态，提示“模拟中不可删除星体”。

删除时还会顺手：

- 关闭三星模式
- 销毁目标节点
- 广播 `PlanetUpdated`

---

## 12. 相机与交互控制

## 12.1 `FreeCameraController`

这个控制器负责：

- 鼠标右键旋转视角
- 滚轮缩放
- WASD/QE 自由移动
- 左键射线选中星球
- F 聚焦 / 取消聚焦
- Esc 退出聚焦
- 显示选中特效

## 12.2 射线拾取

用户左键点击时：

1. 用摄像机把屏幕点转成射线
2. 调用物理系统 `raycast`
3. 遍历命中的碰撞体
4. 用 `PlanetService.getPlanetByNode()` 找到对应行星
5. 设置当前选中行星 ID
6. 显示选中特效
7. 广播 `FocusPlanetChanged`

这说明当前系统的“选中”是以物理碰撞体为入口的。

## 12.3 聚焦模式

控制器内部定义两种模式：

- `LookAt`
- `Follow`

### LookAt

- 相机位置不变
- 朝向持续看向目标

### Follow

- 目标星球作为跟随中心
- 相机沿“质心 -> 行星”的方向保持一定距离
- 相机会始终看向行星
- 滚轮控制跟随距离
- 跟随时 WASD 自由移动被抑制

这套设计很适合教学演示：

- LookAt 适合静态观察轨道
- Follow 适合贴近观察某一颗行星的运动

## 12.4 选中特效

选中特效使用：

- 半透明球体
- 呼吸缩放动画

实现上是给目标节点挂一个子节点 `select_highlight`，并用 `tween` 做循环缩放。

这说明相机控制器不仅承担输入处理，也兼顾了“焦点反馈”的表现层工作。

---

## 13. 驱动器与运行时更新

## 13.1 `SkyController`

`SkyController` 是系统每帧更新的驱动组件。

它主要做三件事：

1. 在编辑器里控制三星布局同步开关
2. 在运行时初始化主相机 `geometryRenderer`
3. 在模拟状态下每帧调用 `PlanetService.update(dt)`

### 为什么不直接让 `PlanetService` 自己每帧跑

因为 `PlanetService` 是服务对象，不是 Cocos `Component`，它没有天然的 `update` 生命周期。

所以需要一个场景组件来承担：

- 引擎生命周期接入
- 每帧调度

这也是典型的“Service + Driver”结构。

---

## 14. 运行流程全景

一个完整的行星系统运行过程，可以概括为：

1. 启动时注册 `PlanetService`
2. 进入 `star.scene`
3. 场景中的 `PlanetItem` / `StarItem` 自动注册到服务
4. `PlanetUI` 同步生成属性面板
5. 用户在编辑状态调整：
   - 质量
   - 初速度
   - 位置
   - 轨迹/受力显示
6. 用户点击“开始模拟”
7. `PlanetService.start()`：
   - 记录初始位置
   - 自动计算初始轨道速度
   - 预先更新一次力
8. `SkyController.update()` 持续驱动 `PlanetService.update(dt)`
9. `PlanetService` 按固定步长做 Verlet 积分
10. `PlanetItem.updateState()` 绘制轨迹与受力
11. 若无恒星且至少两颗行星，更新质心小球
12. 用户可通过相机自由观察、聚焦或暂停
13. 用户点击“重置”时回到开始前状态

## 15. 当前系统的优点

从工程角度看，这个系统已经具备比较完整的雏形，优点明显：

### 15.1 架构清楚

- 服务层、表现层、输入层分工明确
- UI 没有侵入物理核心
- 相机没有耦合 UI 面板

### 15.2 物理推进比一般演示脚本更正规

- 有固定时间步
- 有 Velocity Verlet
- 有力和加速度的分步更新

这比简单的“每帧 v += a*dt, p += v*dt”要稳得多。

### 15.3 可交互性强

- 可增删星体
- 可调整参数
- 可切换三星模式
- 可聚焦观察
- 可画轨迹和受力

### 15.4 编辑器友好

- 编辑器移动行星可以触发三星布局同步
- 参数可以直接在面板中调
- 适合做教学演示与实验玩法

## 16. 当前系统的边界与不足

这部分非常重要，因为它决定了下一阶段开发重点。

## 16.1 有恒星时忽略行星间相互引力

当前一旦 `_hasStar = true`，系统只算恒星对行星的力，不算行星之间的作用。

### 影响

- 适合基础轨道演示
- 不适合展示摄动、多体扰动等更真实的轨道行为

## 16.2 恒星本身不参与动态运动

恒星只是引力源，当前没有作为运动体进入积分更新。

### 影响

- 不能模拟双星恒星系统
- 不能模拟恒星被行星反拖动的效果

## 16.3 通用 N 体初值生成缺失

除了：

- 有恒星
- 双星
- 三星

其它任意构型没有自动平衡初值方案。

### 影响

多行星系统大多需要用户自己猜速度，否则很容易直接崩散。

## 16.4 碰撞模型太简单

现在碰撞后只是停止。

### 可能的改进方向

- 弹性碰撞
- 合并为更大质量天体
- 动量守恒后的新速度
- 生成爆炸特效

## 16.5 部分字段和实现不完全一致

例如：

- `SkyController.isDrawOrbit` 当前没有真正参与轨迹控制分支
- 注释里的“质心小黑球”与实际白球颜色不一致
- `PlanetSystemType` 枚举未在当前代码路径中使用

这说明系统仍处在“可运行但未彻底整理”的阶段。

## 17. 推荐的后续迭代方向

如果后面继续做，这个系统建议按下面顺序升级。

## 17.1 第一阶段：稳定性和清理

优先做：

- 清理 `planetItem.ts` 中疑似误输入字符
- 清理未使用字段/枚举
- 统一注释与实际表现
- 补充对质量为 0、距离过近等异常参数的保护

## 17.2 第二阶段：物理能力升级

优先做：

- 有恒星时支持行星间引力开关
- 恒星进入动态积分
- 支持更多体数量的自动初值生成
- 支持碰撞合并/吞噬

## 17.3 第三阶段：可视化升级

优先做：

- 轨迹颜色按速度或质量变化
- 速度矢量显示
- 能量和角动量监控面板
- 质心轨迹显示

## 17.4 第四阶段：玩法升级

优先做：

- 预设天体模板
- 保存/读取系统配置
- 教学任务引导
- 特定关卡目标，例如“让双星稳定运行 30 秒”

---

## 18. 开发实现建议

如果以后由你继续开发，建议遵循下面的实现原则：

1. 所有全局状态继续收口到 `PlanetService`  
   不要把系统状态拆散到 UI 和各个组件里。

2. 新交互优先通过事件广播接入  
   不要让属性面板直接深度调用多个子模块。

3. 物理算法改动尽量集中在 `PlanetService`  
   `PlanetItem` 更适合只做状态承载和可视化。

4. 相机逻辑尽量只读数据，不写系统状态  
   除“当前聚焦对象”外，尽量不要让相机控制器干预物理计算。

5. 保持“编辑态”和“模拟态”的清晰边界  
   当前系统这部分做得不错，后续不要破坏。

## 19. 一句话总结

这个行星系统的本质是一个**以 `PlanetService` 为核心、采用固定步长 Velocity Verlet 积分、支持恒星/双星/三星教学场景、并通过 UI 与相机交互形成完整可视化实验流程的三维物理模拟模块**。

它现在已经具备：

- 可编辑
- 可模拟
- 可观察
- 可重置
- 可扩展

的基础能力，是一个非常适合继续演化成“教学实验系统”或“互动演示关卡”的良好基础。
